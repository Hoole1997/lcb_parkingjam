# 第一部分：产品需求文档

## 1. 产品概述

### 1.1 背景

当前项目是一个已接入 Launcher、广告聚合、Firebase 和统计能力的 Android APP 模板，尚无正式游戏业务。产品计划将模板改造成竖屏、单手操作、包含大量关卡的挪车解谜游戏。

市场已经验证“一点即走、按顺序清空停车场”具有低理解成本和较强广告变现能力，但同类产品普遍存在以下问题：

- 关卡重复，只增加车辆数量而不增加结构变化。
- 难度或随机结果被怀疑服务于广告扩位、续关或道具消费。
- 广告展示过早、过密，广告时长超过单关游戏时长。
- 活动进度、奖励、去广告权益或重装进度不可靠。
- 金币与长期系统缺少真实消费点。

本产品不以“机制最多”为目标，而以“核心清楚、关卡公平、反馈爽快、广告克制、进度可靠”为竞争点。

### 1.2 一句话产品定义

一款竖屏单手操作的 2D/2.5D 停车场解谜游戏：玩家点击朝向明确的车辆，按照正确顺序将它们驶出停车场，并在章节挑战中优先救出救护车、消防车等特殊车辆，逐步修复城市街区、收集车辆外观。

### 1.3 核心价值

- **三秒理解**：观察车头，点击能安全驶出的车辆。
- **短局满足**：普通关目标时长 15–60 秒，Boss 关 60–120 秒。
- **公平解谜**：所有主线关均有不看广告、不使用道具的可行解证明。
- **持续目标**：通过地区、车库、皮肤和每日挑战提供长期进度。
- **离线可玩**：无网络时仍可进入主线、保存进度和使用已拥有内容。

### 1.4 产品目标

| 编号 | 目标 | 成功定义 |
|---|---|---|
| OBJ-01 | 建立低门槛核心循环 | 新用户无需文字说明即可完成第 1 关；第 5 关前掌握朝向、阻挡和碰撞 |
| OBJ-02 | 支撑长期关卡生产 | 关卡数据化，具备编辑、求解、难度评分、重复检测和解法回放能力 |
| OBJ-03 | 保持关卡公平 | 100% 主线关不依赖广告、付费、随机变色或精确到帧的操作 |
| OBJ-04 | 建立可控商业化 | 广告统一受资格策略、冷却、会话上限和日上限控制，不由页面自行决定 |
| OBJ-05 | 保证进度可靠 | 关卡、奖励、广告发奖和购买权益均支持幂等与恢复，不因进程死亡重复或丢失 |
| OBJ-06 | 适配现有模板 | 复用 Launcher、广告和统计能力，游戏规则不直接依赖任何 SDK |

### 1.5 非目标

首发版本明确不做：

- 真实驾驶模拟、方向盘、油门、刹车或开放世界。
- 真实多人实时对战。
- Bus Out 式乘客颜色排序主循环。
- 体力系统、强制等待和付费随机宝箱。
- 依赖服务端才能进入的主线关卡。
- 通过运行时随机改变车辆、出口、时间或颜色制造难度。
- 在棋盘操作区域放置 Banner、Native 或伪装成游戏按钮的广告。

## 3. 用户与使用场景

### 3.1 核心用户

| 用户类型 | 诉求 | 产品响应 |
|---|---|---|
| 碎片时间用户 | 30 秒到 3 分钟内获得一次完整反馈 | 短关、快速重试、自动保存、单手操作 |
| 放松型解谜用户 | 有思考但不希望持续计时或高惩罚 | 普通关无计时、三点安全点、失败免费 |
| 关卡挑战用户 | 希望有明确的高难内容和成绩证明 | Hard、Boss、每日挑战、无碰撞三星 |
| 收集型用户 | 希望长期拥有可见目标 | 车库、皮肤、尾迹、地区装修、收藏册 |
| 广告敏感用户 | 不希望每关被打断 | 新用户保护、统一频控、奖励广告自愿选择、去广告权益 |

### 3.2 典型场景

- 通勤或排队时连续玩 3–10 关。
- 睡前进行无计时的放松解谜。
- 每日上线完成一关固定挑战并领取收藏进度。
- 无网络时继续主线，联网后补传进度与数据。
- 卡关时先获得免费提示，再自主选择金币或奖励广告帮助。

## 4. 核心体验循环

### 4.1 单关循环

1. 加载已经验证的关卡数据。
2. 玩家观察车辆朝向、出口、阻挡和机关。
3. 点击车辆。
4. 系统计算直线路径与动态冲突：
   - 路径安全：车辆驶出，棋盘状态更新。
   - 路径受阻：车辆短距离碰撞后回位，并按当前模式扣除 1 点安全点。
5. 重复操作直至完成目标或安全点耗尽。
6. 播放清场反馈，计算星级与首次通关奖励。
7. 进入结算、地区进度、下一关。

### 4.2 长线循环

P0 循环：主线通关 → 获得星星/金币 → 解锁基础外观、下一节点和地区 → 开启新机制/Boss → 返回主线。

P1 启用后的扩展循环：获得车辆零件 → 修复地区/扩展收藏 → 进入 Hard、每日或周末救援挑战 → 返回主线。

### 4.3 首次用户流程

| 阶段 | 流程要求 |
|---|---|
| 首次进入 | Launcher 进入游戏后先处理必要隐私流程；不得在隐私状态未明确前请求个性化广告 |
| 第 1 关 | 直接进入关卡，不先展示复杂首页、签到、礼包或广告 |
| 第 1–3 关 | 仅保留棋盘、关卡号、暂停；隐藏金币、车库、活动 |
| 第 4 关后 | 展示简化地图与“继续”按钮 |
| 第 5 关 | 解锁金币界面并发放一次性新手金币 |
| 第 10 关 | 解锁基础外观入口、首个车辆皮肤和小 Boss 奖励 |
| 第 15 关 | 解锁护盾并赠送 1 个；不强制立即使用 |
| 第 20 关 | 解锁拖车；若 P1 已启用，同时开放车库收藏扩展和地区修复 |
| 第 30 关 | 解锁第二地区；若 P1 已启用，同时开放每日挑战和完整 Hard 入口 |

### 4.4 回流用户流程

- 首页第一主按钮始终是“继续第 N 关”。
- 离开 7 天及以上的玩家先进入一关已学机制的简单回忆关或获得明显的简单主线关，不直接弹出多个活动。
- 首页同时可见的强运营入口最多 3 个，其余放入活动中心。
- 离线时隐藏依赖网络且无缓存的入口，不显示不可点击的广告占位。

## 6. 版本范围

### 6.1 P0：首发必需

- 完整的一点即走主线循环。
- 首页/地图、游戏、暂停、失败、结算、设置。
- 120–150 个正式关卡和 50–100 个内容缓冲。
- L26-H 单次 Hard 预览节点属于 P0，用于验证高难接受度；完整 Hard 入口和持续内容仍为 P1。
- 墙、开放边界、双出口、长车、外部车流、按钮门、红绿灯、救援目标、锁/钥匙、Boss。
- 本地版本化存档、离线模式、奖励账本。
- 金币、提示、护盾、拖车和基础皮肤消费点。
- 关卡编辑、求解、评分、重复检测和解法回放工具链。
- 统一广告资格策略、奖励广告和低频结算插屏。
- 核心埋点、广告收益、崩溃和存档恢复监控。
- 隐私、Data Safety 所需产品入口与状态控制。

### 6.2 P1：非 P0，可选择随首发启用或首发后追加

- 车库收藏扩展、尾迹、地区修复和收藏册。
- 每日挑战、Hard 模式、周末救援挑战。
- 云存档、恢复购买、永久去广告商品。
- 远程关卡包、活动中心、补签和异常奖励补发。

### 6.3 P2：验证后候选

- 乘客颜色排序独立模式。
- 无尽模式、赛季、排行榜、历史幽灵对手。
- 更复杂的装修经济或长期建造。
- iOS 或其他平台版本。

## 8. 视觉、音频与交互要求

### 8.1 视觉

- 俯视 2D/2.5D，车辆朝向在缩小状态下仍能一眼识别。
- 不只依赖车身颜色表达规则；特殊状态同时使用图标、描边、纹理或动画。
- 车辆点击热区可略大于模型，但不得覆盖相邻车辆中心区域。
- 可驶出路径使用柔和引导；被阻挡路径用短暂红色提示，不持续污染棋盘。
- 墙、出口、关闭门、打开门、按钮、锁和动态车流必须具有不同轮廓。
- 游戏内不出现车辆撞击行人的表现；车辆对行人只允许刹停或等待。

### 8.2 动效

- 安全驶出：加速、轻微转向出画、尾迹和连续出车连击反馈。
- 碰撞：短距离位移、弹性回位、轻震动，不改变逻辑位置。
- 清场：最后一个目标条件相关的离场动画完成后再进入结算；救援关不等待无关车辆清空，且不允许广告截断胜利反馈。
- 开启“减少动态效果”后缩短位移、关闭镜头缩放与强震动，但保留状态可读性。

### 8.3 音频与震动

- 音乐、音效、震动三个独立开关。
- 不同车辆可共享声音层，不要求首发每辆车独立录音。
- 碰撞、机关、解锁、清场、奖励到账必须有可区分反馈。
- 广告返回后不得叠加播放暂停前的音效或音乐实例。

# 第二部分：核心规则文档

## 11. 文档目的与规则优先级

本部分是客户端、关卡编辑器、求解器、测试用例和数据分析的共同判定依据。同一局面在不同帧率、设备或恢复路径下必须得到相同结果。

当配置与规则冲突时，按以下优先级处理：

1. 安全与合规规则；
2. 本核心规则文档；
3. 经版本化的关卡配置；
4. 动画、音效等表现配置；
5. 远程实验参数。

远程配置只允许调整数值、开关和展示节奏，不允许在线改变车辆占格、碰撞和胜负等基础语义。基础语义变化必须升级 `rule_version` 并回归所有正式关卡。

## 12. 术语与棋盘模型

### 12.1 关键术语

| 术语 | 定义 |
|---|---|
| 一次尝试 Attempt | 从进入关卡可操作状态开始，到完成、失败或主动退出为止；重开产生新的 `attempt_id` |
| 尝试链 Attempt Chain | 初始尝试及其至多一次广告续关组成的成绩范围；免费重试创建新的 `attempt_chain_id`，广告续关创建新 `attempt_id` 但沿用原链 |
| 稳定状态 Stable State | 棋盘上没有碰撞回弹、机关切换或尚未提交的车辆移动，可安全保存和继续判定的状态 |
| 前方射线 Forward Ray | 从车辆车头占格之外，沿车辆朝向延伸到可离场边界的有序格子与边界段 |
| 阻挡物 Blocker | 会阻止车辆当前合法离场的场内车辆、墙、关闭的门或未满足的锁；已提交车辆的动画路径不属于规则阻挡物 |
| 必要车 Required Vehicle | 必须离场才满足当前目标的车辆；救援关可以只有救援目标是必要车 |
| 安全点 Safety | 玩家允许发生“计次碰撞”的剩余次数；不是生命购买门槛 |
| 标准解 Canonical Solution | 关卡发布时随配置保存的一条无道具、无广告、无需精确抢时的合法解法 |
| 按钮门 / 压力板门 | 首发统一指“车辆触发地面压力板后，绑定闸门永久打开”的机关；文案可简称按钮门 |

### 12.2 坐标和占格

- 棋盘原点为左上角 `(0,0)`，`x` 向右增加，`y` 向下增加。
- 逻辑计算只使用整数格和确定性状态；像素、缩放比例和动画插值不得参与碰撞判定。
- 推荐正式关卡范围为 5×6 至 10×12 格。超出范围需要单独验证小屏可读性和性能。
- 静止车辆必须完整占据格子，不允许两个实体初始重叠，也不允许半格停车。
- `N/E/S/W` 分别表示向上、右、下、左；车辆只能沿自身朝向向前驶出，不能倒车、转向或拖拽。
- 棋盘边界由“可离场出口段”和“封闭边界段”组成。车辆只有在前方射线连接到可用出口时才能离场。

### 12.3 默认车辆规格

| 类型 | 基础占格 | 用途 | 默认是否可被拖车 |
|---|---:|---|---|
| 小汽车 `car` | 1×2 | 主要解谜实体 | 是 |
| 卡车 `truck` | 1×3 | 增加长占格和视线判断 | 是 |
| 救护车/消防车 `rescue` | 默认 1×2；Boss 可显式配置 1×3 | 救援目标 | 否 |
| 钥匙车 `key_car` | 1×2 | 离场后解除绑定锁 | 否 |
| 特殊剧情车 `special` | 配置限定 | Boss 或剧情用途 | 默认否 |

占格按朝向旋转。例如基础 1×2 的车朝东/西时占据横向 2 格，朝北/南时占据纵向 2 格。每辆车必须有稳定唯一的 `vehicle_id`，颜色和皮肤只用于辨认，不改变规则。

## 13. 车辆状态机与输入

### 13.1 状态

| 状态 | 含义 | 可否响应点击 |
|---|---|---:|
| `parked` | 停在棋盘，可能可离场或被阻挡 | 是 |
| `locked` | 被锁定，需先满足解锁条件 | 是，仅反馈原因，不移动 |
| `moving` | 已提交离场并从逻辑占格移除，动画正在播放或排队 | 否 |
| `waiting` | 已逻辑离场，在棋盘外安全线等待红灯或外部交通放行 | 否 |
| `collision_return` | 正在播放前冲与回弹 | 否 |
| `towed` | 被拖车合法移除的终态，记录 `exit_reason=tow` | 否 |
| `exited` | 驶出动画完成的表现终态；规则意义与已提交离场相同 | 否 |

合法状态迁移为：

```text
locked -> parked -> moving -> waiting(可选) -> exited
                  \-> collision_return -> parked
                  \-> towed
```

车辆从 `parked` 进入 `moving` 时即原子设置 `exit_committed=true`，释放逻辑占格并参与目标判定。动画回调只允许把 `moving/waiting` 更新为表现态 `exited`，不得决定碰撞、胜负或奖励；零动画测试也必须得到相同规则结果。拖车则直接进入 `towed`，是否可计入目标由目标类型和车辆标签决定。

### 13.2 点击处理顺序

点击命中多层视觉元素时，只选择可见车身最上层且逻辑占格包含点击点的车辆。单次点击按以下顺序处理：

1. 页面、棋盘或尝试是否处于可输入状态；
2. 是否命中车辆；
3. 车辆是否为 `parked` 或 `locked`；
4. 若锁定，展示锁和前置条件，不扣安全点；
5. 计算前方射线、出口和静态阻挡；
6. 若静态阻挡，提交一次碰撞；
7. 若路径合法，原子提交离场、机关和保存状态；
8. 将扫掠路径交给表现调度器：不相交则并行动画，相交则按提交顺序排队动画。

快速重复点击同一辆车只处理第一次。输入去抖建议 120 ms，但去抖不得吞掉对另一辆独立车辆的正常点击。

## 14. 离场、路径和并行动画规则

### 14.1 合法离场条件

车辆可离场必须同时满足：

- 车辆状态为 `parked`；
- 从车头到匹配出口的射线上无其他未离场车辆；
- 射线上无墙、关闭的门或未满足条件的障碍；
- 出口允许该车辆类型通过；
- 关卡未处于暂停、结算、广告切换或存档恢复过程。

满足条件后，车辆在逻辑层立即标记为已提交离场并释放原占格。表现调度器单独保存扫掠路径，解决动画先后和穿模，但不得反向改变本次规则提交。

### 14.2 多车连点

- 允许玩家连续点击互不冲突的车辆，形成流畅的多车离场效果。
- 几何上不相交的扫掠路径可以并行动画；相交路径永不同时播放，后提交动画进入 FIFO 队列。
- 动画排队不拒绝已合法提交的操作，不产生碰撞，也不改变星级。重复点击已提交车辆仍被去重。
- 动画速度、设备帧率和“减少动态效果”只影响何时播完，不影响某次点击是否被规则接受。
- 求解器以串行操作验证标准解，因此任何正式关卡都不能依赖多指或精确并发才能完成。
- 目标已经逻辑达成时，停止接收新输入；等待相关已提交动画结束后再显示结算。

### 14.3 移动时长

动画速度允许按屏幕距离做有限缩放，普通车辆从点击到完全离场建议 350–900 ms。规则层不依赖这一时长；测试环境可以零动画逐步执行标准解。

## 15. 阻挡、碰撞与安全点

### 15.1 计次碰撞

以下行为算一次计次碰撞：

- 点击车辆后，其正前方被另一辆静止车辆挡住；
- 前方被实体墙或关闭的闸门挡住；
- 车辆没有朝向任何可用出口，却尝试驶向封闭边界。

表现为前冲约 0.2–0.35 格、轻微碰撞反馈并返回原位，总时长建议不超过 450 ms。车辆不得推动、旋转或损坏阻挡物。

碰撞判定成立时，规则层先原子提交 `collision_count + 1`、安全点变化和存档，再播放回弹。若进程在动画中结束，恢复时车辆回原占格，但已提交的碰撞和安全点保持，不重复扣减。

以下行为不扣安全点：点击锁定车、点击空白、点击 UI、红灯等待、礼貌避让行人、广告或系统中断造成的取消。

L1–L5 中任何阻挡反馈统一标记 `collision_kind=tutorial_demo`：只累计 `tutorial_mistake_count`，不进入正式 `collision_count`、不扣安全点、不降低星级，也不触发 `collision` A 级事件；受控引导点击另补 `tutorial_action=guided_mistake`，但不改变规则结果。

### 15.2 安全点规则

| 模式 | 初始安全点 | 附加规则 |
|---|---:|---|
| 教学关 L1–L5 | 不扣减 | 所有阻挡反馈按 `tutorial_demo` 处理，不能失败或降星 |
| 普通主线 | 3 | 降为 0 时失败 |
| Hard 支线 | 1 | 进入前明确展示；不阻断普通主线 |
| Boss | 默认 3 | 可经关卡配置提高，但不得临时远程降低 |

- 每次计次碰撞最多扣 1 点，并使“零碰撞”三星条件失效。
- 护盾在玩家主动使用时立即把安全点恢复 1 点，最高不超过该关初始值；满安全点时不可使用且不消耗。它不拦截后续碰撞。
- 当安全点因碰撞降到 0，规则事务立即把 `attempt_state=fail`、`presentation_state=failure_pending` 并锁定全部棋盘输入；完成碰撞回弹后只负责展示失败面板，期间不能再驶出车辆或抢先完成目标。
- 致命碰撞事务已经保存车辆原逻辑占格、`safety=0` 和失败业务终态；回弹完成后直接把该已存局面作为失败稳定快照。奖励广告续关恢复该局面并把安全点**设置为 1**，不是在碰撞前数值上再加 1，也不重新判定失败。

## 16. 机关与动态元素

### 16.1 墙和出口

- 墙可以占格或封闭一段边界；其碰撞范围由逻辑格决定。
- 墙用于形成车道、出口缺口和可读边界；在 `CLEAR_ALL/BOSS_CLEAR` 中，发布校验必须拒绝任何必要车被永久墙或封闭边界挡死的布局。只有可由单调机关打开的门可以暂时阻挡必要车。
- 同一关可有多个出口。出口可限制朝向或车辆类型，但必须在进入关卡时有明确视觉区分。
- 出口不能在一局中无提示地改变位置。

### 16.2 压力板与闸门

- 触发车 T 的已验证离场路径经过指定压力板 S；T 的离场动作提交时，绑定闸门 G 在规则层同步永久打开。
- 门动画仅表现已经提交的 `open` 状态；后续车辆可按新规则状态提交，表现调度器负责避免与开门动画穿模。
- 首发门不自动关闭，也不允许 T 依靠自己尚未触发的 G 才能到达 S，发布校验必须拒绝这种自依赖。
- 一块压力板可绑定多个门，配置中必须显式列出关系。

### 16.3 钥匙车与锁定车

- 钥匙车成功离场后，所有绑定的锁定车转为 `parked`。
- 点击锁定车只提示所需钥匙车，不扣安全点。
- 钥匙关系不能形成循环依赖；发布校验必须拒绝此类配置。

### 16.4 信号灯、外部车流和行人

这些元素用于制造观察感和节奏，不制造需要“抢帧”的解法：

- 红灯时，玩家车辆可开到停止线并进入 `waiting`；绿灯后自动继续，不扣安全点。
- 外部车流必须有清晰可见的接近方向。若当前窗口不安全，玩家车辆在停止线自动等待，不能发生真实撞车。
- 行人进入路径时车辆自动礼让；行人不能被撞击，也不作为失败来源。
- 单次自动等待的设计目标不超过 3 秒；若设备切后台，动态元素与等待车辆一并冻结。
- 标准解只验证操作顺序，不要求某一秒点击。动态元素故障或资源缺失时必须降级为安全放行。

### 16.5 首发机关复杂度限制

- L1–L10 每关最多 1 种新概念；L11–L20 同时最多 2 种机关；L21–L30 同时最多 3 种。
- 同一视觉符号不能在不同关卡表达不同语义。
- 首发不加入可逆门、车辆转弯、倒车、传送、隐藏阻挡或物理推挤。

## 17. 目标、胜负与中断

### 17.1 目标类型

| 目标枚举 | 完成条件 | 用途 |
|---|---|---|
| `CLEAR_ALL` | 所有必要车均已 `exit_committed`，或在允许拖车时为 `towed` | 普通关和多数 Boss |
| `RESCUE_TARGET` | 指定救援车以正常驾驶方式提交离场 | 剧情救援关；目标固定禁拖，其他车可留在棋盘 |
| `BOSS_CLEAR` | 清空必要车并满足关卡指定机关条件 | 大棋盘章节关；逐关明确是否采用救援子目标 |

可选时间勋章只影响额外展示或活动任务，不影响主线完成、基础奖励和解锁下一关。首发主线不得设置强制倒计时失败。

### 17.2 完成、失败和退出

- 完成：最后一个目标条件在逻辑层达成时立即锁定输入，等待相关离场动画完成后显示结算。
- 失败：安全点归零时立即提交失败业务终态并锁定输入；等待碰撞回弹结束后显示失败面板。
- 主动退出：玩家从暂停页离开，记录为 `quit`，不是 `fail`。
- 重开：先以 `quit/restart` 终结旧 Attempt，清除临时机关和道具效果，再从发布初始布局创建新的 `attempt_id + attempt_chain_id`；链碰撞、`continue_used`、护盾/拖车使用标记归零，但已实际消耗的库存或金币不退款。
- 若目标已逻辑完成后应用进入后台，恢复时直接完成余下表现并进入结算，不能回到可操作棋盘。

Attempt 业务状态只允许：

```text
active → complete
active → fail
active → quit
active → content_error
```

目标达成或安全点归零时，业务终态、棋盘输入锁、`presentation_state=completion_pending/failure_pending` 与 `level_end` outbox 在同一原子事务提交。表现完成只把 `presentation_state` 改为 `presented`，不得改变业务终态；pending 期间不允许再处理棋盘业务输入，也不能同时转入另一终态。

### 17.3 暂停、后台、广告和进程恢复

- 暂停时冻结输入、游戏动画、动态车流、计时和音频。
- 展示广告前必须先到达或构造稳定保存点；不得在碰撞回弹中间弹广告。
- 若应用在车辆移动中被系统杀死，恢复时按已提交的逻辑结果重建：合法离场车保持离场，碰撞车回到原占格。
- 快照至少包含：`level_id`、`level_version`、`rule_version`、`attempt_id`、`attempt_chain_id`、`attempt_state`、`presentation_state`、`continue_used`、已提交离场/拖走车辆、机关状态、安全点、链累计碰撞数、已用道具、已发奖励交易、可选计时状态。
- 关卡版本不兼容时，不猜测迁移局面；保留玩家已完成记录和消耗，以该关最新初始布局重新开始并给出简短说明。

## 18. 星级、奖励与道具

### 18.1 星级结算

| 星级 | 条件 |
|---:|---|
| 1 星 | 完成且尝试链累计发生 2 次及以上计次碰撞 |
| 2 星 | 完成且尝试链累计恰好发生 1 次计次碰撞 |
| 3 星 | 完成且尝试链累计没有计次碰撞 |

- 使用提示不降低星级。
- 使用护盾补点后发生的碰撞仍按一次碰撞计算。
- 使用拖车完成后该尝试链最多获得 2 星。
- 重玩只覆盖更高历史星级，不降低已记录最佳成绩；首次通关奖励只发一次。

### 18.2 基础奖励

默认值由版本化经济配置提供。普通关 1/2/3 星完整首通总额分别为 20/25/35；小 Boss 以 60 为基础、大 Boss 以 120 为基础，2 星再加 5、3 星累计加 15。重复通关默认不发首次奖励，只在首次提高历史星级时补足到对应完整总额。

奖励结算通过唯一 `reward_transaction_id` 记账。结果页动画、广告回调或进程恢复重复触发时，不得重复入账。

### 18.3 道具规则

| 道具 | 入口与效果 | 限制 | 星级影响 |
|---|---|---|---|
| 提示 `hint` | 高亮标准解在当前状态下的下一辆安全车，并显示方向 | 每次只揭示一步；状态偏离标准解时由求解器实时寻找安全步；找不到则不消耗 | 无 |
| 护盾 `shield` | 主动使用后立即恢复 1 个安全点 | 满安全点不可用；不超过初始上限；每个尝试链至多使用 1 次 | 后续碰撞照常计数 |
| 拖车 `tow` | 选择允许拖走的 `parked` 车辆并置为 `towed` | 每个尝试链至多 1 次；所有 `tow_prohibited=true`、救援/剧情目标车、钥匙车、触发车、锁定车不可选；普通 `CLEAR_ALL` 必要车是否可拖仅由不可变标签决定 | 尝试链最多 2 星 |
| 继续 `continue_shield` | 失败页通过奖励广告恢复 `safety=0` 的失败稳定快照，再将其设置为 1 | 整个尝试链至多 1 次；创建子 `attempt_id`；不是强制入口 | 链内原碰撞记录保留 |

道具可由库存、金币或奖励广告提供，但一次入口只能明确展示一种支付方式。扣库存/金币与效果提交必须原子化；效果无法执行时不消耗。

Hard 与 Hard Preview 初始安全点为 1，采用“立即补点”模型时没有合法的局内护盾使用窗口，因此这两种模式默认隐藏并禁用护盾；失败后的自愿广告续关仍按独立 `continue_shield` 规则处理。

## 19. 可解性、公平性与难度

首发采用严格的“单调状态”设计：合法离场只会减少车辆，门只会打开，锁只会解除，已获得的钥匙和已激活的压力板不会回退。因此任意当前合法车辆都应该可以放心驶出，不能存在“虽然能走，但先走这辆就进入死局”的隐藏陷阱。

基于这一约束，首发不提供撤销：合法操作无后悔，错误点击也不改变棋盘位置。若未来加入车辆换位、转向、可逆门或会重新增加阻挡的机制，必须重新设计撤销、存档和求解规则。

### 19.1 发布硬门槛

每个正式关卡必须通过以下自动校验：

1. 初始占格、边界和引用关系合法；
2. 存在至少一条不使用道具和广告的解法；
3. 保存一条可回放的标准解及其最少/推荐步数；
4. 解法不依赖帧率、多指、音频提示或小于 1.2 秒的点击窗口；
5. 不存在钥匙循环、目标不可达、门引用丢失或出口类型冲突；
6. 每辆必要车最终均可连接至匹配出口；永久墙或封闭边界不能成为其不可解除的正向阻挡；
7. 在目标设备的最小棋盘显示尺寸上，车辆仍可可靠点击；
8. 与已发布关卡的结构签名不属于未批准的近重复。

除找到一条标准解外，发布验证还必须遍历或证明从初始状态可达的所有合法非终局状态仍然可解；发现任一合法操作导致死局，该关不得发布。

自动生成只能产出候选。所有进入正式主线包的关卡都必须逐关人工试玩并签字；缓冲候选先完成自动校验并按批次抽样，任何候选在晋升为正式关前仍需补齐逐关人工签字。

### 19.2 难度指标

关卡编辑器至少输出下列指标：

| 指标 | 含义 |
|---|---|
| `vehicle_count` | 初始车辆总数 |
| `required_count` | 必要车辆数 |
| `solution_steps` | 标准解操作数 |
| `dependency_depth` | 最深阻挡依赖链长度 |
| `safe_first_moves` | 初始可安全离场车辆数 |
| `false_affordances` | 看似接近出口但当前被挡的车辆数 |
| `mechanic_count` | 同时参与解法的机关种类数 |
| `board_density` | 车辆占格/可停放格比例 |
| `branching_mean` | 解法过程中平均安全选择数 |

初始难度分可按“车辆数、依赖深度、密度、假线索、机关数增加，安全首步与平均分支降低”计算，但只用于排序候选。上线后以完成率、碰撞率、尝试次数和时长重新标定，不能只依赖公式。

### 19.3 重复检测

- 为棋盘生成规范化结构签名，比较车辆占格、朝向、类型、出口、墙和机关关系。
- 旋转、镜像后仅换色或换皮肤的布局默认视为重复。
- 允许为教学目的复用局部结构，但必须有新的学习目标并经设计标记。
- 连续 5 关不能使用相同的开局安全车位置与同构依赖链。

## 21. 关键边界用例与验收

| 编号 | 场景 | 预期结果 |
|---|---|---|
| RULE-ACC-001 | 同一车被 5 次快速点击 | 只提交一次移动或一次碰撞，不重复扣点 |

| RULE-ACC-004 | 碰撞恰使安全点为 0 | 同事务锁输入并提交唯一失败终态；回弹后只显示面板，不可抢先出车或完成 |
| RULE-ACC-005 | 失败时奖励广告继续并重复回调 | 链内只续关一次；从 `safety=0` 设置为 1，不重复奖励 |
| RULE-ACC-006 | 红灯或行人位于出口外 | 车辆安全等待并自动继续，不算碰撞 |
| RULE-ACC-007 | 车辆移动时锁屏并杀进程 | 恢复后局面符合已提交逻辑，无复制或丢车 |
| RULE-ACC-008 | 最后一辆离场时切后台 | 恢复后进入已完成结算，不可再次领奖 |
| RULE-ACC-009 | 新关卡包损坏 | 回退内置包，存档和已领奖记录不丢失 |
| RULE-ACC-010 | 使用拖车移除普通车 | 关卡可继续，最终星级上限为 2 |
| RULE-ACC-011 | 拖车选择钥匙车或救援车 | 不可选且不消耗库存/广告奖励 |
| RULE-ACC-012 | 标准解在零动画测试模式回放 | 每次得到相同完成结果和步数 |
| RULE-ACC-013 | 暂停或广告展示期间连续点击 | 不接受棋盘操作，不改变状态 |
| RULE-ACC-014 | 修改表现速度、分辨率或减少动态效果 | 胜负、碰撞、奖励与原结果一致 |
| RULE-ACC-015 | 主动重开已发生碰撞/用过道具的关卡 | 旧 Attempt 以 restart 结束；新 `attempt_id + attempt_chain_id` 且链计数归零，已消费资源不退款 |
| RULE-ACC-016 | Hard/Hard Preview 初始进入 | 护盾按钮隐藏且不可从快捷入口使用；免费重试与符合条件的自愿续关仍可用 |

# 第三部分：前 30 关关卡表

## 22. 关卡表使用说明

本表定义前 30 关的教学目标、依赖骨架、节奏和验收指标，是关卡制作 Brief，不替代编辑器中的最终坐标配置。关卡设计完成后，实际车辆 ID、坐标和标准解必须由编辑器导出并附在关卡包内。

### 22.1 表内符号

- 棋盘使用“宽×高”逻辑格。
- `A→B`：A 必须先离场，B 才能离场。
- `(A+B)→C`：A、B 均离场后 C 才能离场。
- `T[S]⇒G`：触发车 T 成功经过压力板 S 后，永久打开门 G；T 是车辆，S/G 是机关 ID。
- `K⇒Q`：钥匙车 K 离场后，永久解锁车 Q。
- `A×B`：两辆车的动画路径可能交叉；两次合法点击都照常提交，表现层按提交顺序排队，避免动画并发穿模。
- 依赖式中的车辆字母表示“该车已离场”，门字母表示“该门已打开”；例如 `(G1+G2+Q)→R` 表示 G1/G2 已打开且 Q 已离场后，R 才可离场。
- “开局安全车辆数”是无需先处理其他场内车辆或机关即可合法提交的车辆数量，不是解法步数。
- 目标时长是新玩家首次完成的预期中位区间，不是强制倒计时。
- 难度使用 D1–D5：D1 教学/爽关，D2 轻度，D3 中等，D4 困难/小 Boss，D5 地区大 Boss。
- L1–L5 安全点不扣减；普通关 3 点；L26 为一次性的 Hard 预览，1 点。
- `L26-H` 的玩家显示编号仍为 26，内部建议使用 `level_id=main_026` 和 `mode=hard_preview`；它计入本表 30 个设计节点，但完成 L25 即可解锁 L27。
- 除 Boss 特别注明外，首通金币为“20 基础 + 星级附加”。L1–L4 奖励照常入账但隐藏金币 UI，L5 统一揭示余额并额外发 100 新手金币。

### 22.2 全局制作约束

1. 每关都必须有零道具、零广告、零碰撞解。
2. 所有成功动作保持关卡可解，不设计“这辆车虽然能走，但先走就死局”的陷阱。
3. 动态交通只造成最多 3 秒的自动安全等待，不要求玩家抢时间窗。
4. 按钮、门、钥匙、锁、出口和信号灯使用“颜色 + 图形/轮廓”双编码。
5. 新机制关先降低车辆数，机制综合关最多同时使用 3 种已教学机制。
6. 任意连续 6 个必经主线节点内至少安排 1 个低压力/局部回落节点；前 30 关由 L11、L15、L18、L23、L29 承担，避免难度持续单调上升。
7. 失败后免费重试始终是主要按钮之一；广告加载状态不参与关卡开始和通关判定。

# 第四部分：埋点与广告位表

## 27. 数据目标与实施边界

埋点必须能回答四类问题：玩家是否理解玩法、哪一关造成流失、经济是否健康、广告是否在增加收入的同时伤害体验。埋点不是页面日志，只有能支持产品判断或故障定位的事件才进入正式字典。

建议建立两个单一业务入口：

- `AnalyticsRouter`：接收统一业务事件，自动补公共参数、校验枚举、采样并适配 Firebase 等数据端。
- `AdOrchestrator`：接收“广告位机会”，统一完成同意状态、权益、频控、SDK 路由、展示状态和奖励账本；页面不直接调用某个广告 SDK。

若聚合 SDK 已负责 AdMob、Pangle 等网络，应用层不得对同一个广告机会再并发请求多个 SDK。关卡规则不得依赖埋点成功或广告 SDK 可用。

### 27.1 事件等级

| 等级 | 上报策略 | 例子 |
|---|---|---|
| A 业务关键 | 在允许 Analytics 的范围内，100% 的合格事件与业务状态同事务写入耐久 outbox；各目的端按“至少一次”投递，数仓以 `client_event_id` 去重 | 关卡开始/终态、奖励、货币、购买、广告曝光 |
| B 诊断分析 | 默认会话级 10% 稳定采样，或在端上聚合后上报 | 每次车辆点击、车辆离场、路径冲突 |
| C 调试 | 仅 Debug/内部测试包，不进入生产分析 | 每帧状态、完整求解轨迹、碰撞盒明细 |

采样率由远程配置控制，但同一 `game_session_id` 必须稳定命中或不命中，避免一个尝试只有半条事件链。

Firebase 等客户端分析 SDK 不承诺逐事件送达确认，因此“已写 outbox”不等于“服务端已收到”。金币、奖励、购买、关卡进度以本地/服务端业务账本为真相源，不能通过分析事件反推补发。用户拒绝 Analytics 时不创建可在未来补传的行为历史；用户撤回同意时删除尚未投递的 Analytics outbox，但依法必须保留的购买/奖励业务账本走独立受控存储，不进入分析目的端。

## 28. 命名、ID 与公共字段

### 28.1 命名规范

- 事件、参数、枚举统一使用小写英文加下划线，例如 `level_end`、`result=complete`。
- 事件名不写版本、平台和结果；语义变化使用 `event_schema_version`。
- 禁止使用 `firebase_`、`google_`、`ga_` 等保留前缀。
- 时长统一为整数毫秒 `*_ms`；货币收入统一为整数微单位 `*_micros`；数量为整数。
- 未知枚举统一为 `unknown`，禁止上传临时自然语言作为枚举。
- 多值参数使用经过字典约束的稳定排序字符串（例如 `gate,key`），不上传数组或任意 Map。
- 内部事件可映射为 Firebase 推荐事件，但同一行为只允许一个入口上报，避免重复计数。

### 28.2 关键 ID

| ID | 生成与生命周期 |
|---|---|
| `client_event_id` | 每条可重传事件唯一，用于客户端 outbox 与数仓去重；不承诺第三方 SDK 自身去重 |
| `game_session_id` | 冷启动生成；后台超过 30 分钟再回前台时更新 |
| `level_entry_id` | 玩家发起一次进入/恢复关卡时创建；覆盖加载成功或失败，不代表 Attempt 已开始 |
| `attempt_id` | 每次关卡开始、免费重试或广告继续后的新尝试唯一 |
| `attempt_chain_id` | 初始尝试创建；广告续关沿用，免费重试创建新值；星级、护盾和续关次数按链累计 |
| `parent_attempt_id` | 广告继续后的新尝试关联失败尝试；普通开始为空 |
| `completion_id` | 每次成功结算唯一，用于首通、星级和翻倍奖励去重 |
| `ledger_id` | 每一笔金币/道具变动唯一 |
| `preload_id` | 每次预加载决策唯一；预加载尚未绑定页面机会时不得伪造 `opportunity_id` |
| `opportunity_id` | 每次可展示业务机会唯一；仅展示阶段及已绑定具体业务对象的奖励预加载必需 |
| `ad_request_id` | 每次向广告路由发起的加载请求唯一 |
| `ad_show_id` | 每次正式展示尝试唯一 |
| `reward_claim_id` | 奖励广告播放前持久化的奖励承诺唯一 |
| `business_context_id` | 某次广告所服务的业务对象，例如一次失败、一次结算或一次提示机会；用于防止同一对象重复消费 |
| `billing_session_id` | 每次购买流程唯一 |
| `purchase_record_id` | 一笔购买从 `PENDING`、`PURCHASED`、验证、确认、恢复到退款/撤销的稳定业务记录 ID；`billing_session_id` 不能替代它 |

失败已结束旧 `attempt_id`。若玩家看广告继续，恢复旧棋盘快照后必须创建新 `attempt_id`，通过 `parent_attempt_id` 关联，沿用 `attempt_chain_id`、`continue_used=true` 和累计碰撞数。免费重试则创建全新的尝试链。

### 28.3 自动公共参数

| 参数 | 必需 | 示例 / 说明 |
|---|---:|---|
| `client_event_id` | 是 | UUID 或等价唯一值；不注册为高基数自定义维度 |
| `event_schema_version` | 是 | `1` |
| `event_time_ms` | 是 | 业务发生时的原始时间；离线重传不得改成上传时间 |
| `game_session_id` | 是 | 当前会话 |
| `app_version` / `build_number` | 是 | 安装版本与构建号 |
| `build_channel` | 是 | `internal/closed/open/production` |
| `content_version` | 是 | 当前关卡包版本 |
| `screen_name` | 是 | `gameplay/result/home/garage/...` |
| `network_type` | 否 | `wifi/cellular/offline/unknown` |
| `analytics_collection_state` | 是 | `granted/denied/not_required/unknown`；决定是否进入 Analytics outbox |
| `ads_request_mode` | 是 | `personalized/non_personalized/limited/blocked/unknown`；`blocked/unknown` 时不得请求广告 |
| `audience_mode` | 是 | `general/restricted/unknown` |
| `device_tier` | 否 | `low/mid/high` |
| `experiment_variants` | 否 | 仅上传当前相关实验及分组 |

从 `level_start` 起的关卡事件由统一上下文自动补：`level_id`、`level_version`、`chapter_id`、`mode`、`difficulty`、`attempt_id`、`attempt_chain_id`。加载阶段只使用 `level_entry_id`，不得伪造 `attempt_id`。广告事件自动补：`placement_id`、`ad_format`、`sdk_route`、`ads_config_version`；预加载阶段补 `preload_id`，展示机会阶段再补 `opportunity_id`。

不同分析平台参数限制不同时，由路由层做字段投影；业务页面不得为了某个平台复制第二套事件。

### 28.4 字段类型、校验与平台投影

- 正式字典仅允许 `String`、`Long`、`Double` 三种标量。时间、微单位、计数用 64 位 `Long`；布尔映射为 `Long 0/1`；收入 `value_micros` 投影到平台 `value` 时除以 1,000,000 转 `Double`。
- ID 最大 128 个 ASCII 字符，枚举/事件/参数名最大 40 个字符，普通自由文本参数最大 100 个字符；本文未标“可选”的业务参数均不可空。生产环境遇到未知枚举统一投影为 `unknown` 并计校验错误，Debug 构建直接失败。
- 枚举采用封闭列表；错误码至少由所属模块提供 `none/unknown/timeout/offline/invalid_state/sdk_error/storage_error`，模块可追加版本化子码，禁止把异常堆栈或自然语言当错误码。
- Firebase 单事件参数预算按最多 25 个业务参数设计。路由层为每个事件维护确定投影：平台已自动提供的 app/device/session 字段不重复传；被裁剪的高基数字段保留在自有导出/数仓，不注册为 Firebase 自定义维度。
- `attempt_id`、`attempt_chain_id`、`completion_id`、`ledger_id`、`preload_id`、`opportunity_id`、`ad_request_id`、`ad_show_id`、`reward_claim_id`、`business_context_id`、`billing_session_id`、`purchase_record_id` 均只作导出联表键，不注册为 GA4 自定义维度或用户属性。
- 路由层根据产品状态确定性映射 `analytics_storage`、`ad_storage`、`ad_user_data`、`ad_personalization` 等平台 consent signal；业务页面不得自行设置，也不得用“允许非个性化广告”推导“允许 Analytics”。
- M1 结束前必须生成并评审机器可读的 `docs/schemas/analytics_v1.json` 与 `docs/schemas/level_schema_v1.json`，明确每个字段的类型、可空性、长度、枚举和版本；本 PRD 定义语义，但不假装这两个实现制品已经存在。CI 与 Debug 事件检查器必须读取同一份 schema。

Firebase 映射必须只有一个业务入口：

| 内部事件 | Firebase 投影 | 去重规则 |
|---|---|---|
| `screen_view` | 推荐 `screen_view` | 使用手动页面事件时关闭/抑制同页面自动 Screen Reporting，避免一页两次 |
| `level_start` | 推荐 `level_start`，`level_name=level_id` | 每个 `attempt_id` 一次 |
| `level_end` | 推荐 `level_end`，`level_name=level_id`，`success=1/0` | 每个 `attempt_id` 至多一次 |
| `earn_virtual_currency` / `spend_virtual_currency` | 同名推荐事件；使用 `virtual_currency_name,value` | `value` 为普通货币单位数量，不传微单位 |
| `ad_impression_recorded` / `ad_revenue_paid` | 每次曝光只选择自动 AdMob 链路或路由映射的 `ad_impression` 之一 | 统一以 `ad_show_id` 在数仓归并，严禁自动与自定义两份相加 |
| `purchase_result` | 保留为诊断事件；购买收入只选择 Play/Firebase 自动 IAP 或受控手动 `purchase` 之一 | 同一 `purchase_record_id` 只有一个收入来源；不传 purchase token |

## 29. 正式事件字典

下表不重复列出公共参数。标为 A 的交易类事件必须在状态/账本提交成功后上报，而不是在动画开始时上报。

### 29.1 会话与新手流程

| 事件 | 等级 | 触发时机 | 必需业务参数 | 验收口径 |
|---|---|---|---|---|
| `game_session_start` | A | 创建新游戏会话 | `start_type` | 每个会话一次；`cold/warm/resume_after_timeout` |
| `screen_view` | B | 页面真正可见且可交互 | `screen_name, entry_source` | 预加载不算；普通前后台恢复不重复刷屏 |
| `tutorial_start` | A | 首次引导开始 | `tutorial_version, entry_source` | 同一版本默认一次 |
| `tutorial_step_view` | B | 步骤遮罩真正可见 | `step_id, step_index, level_id` | 展示后才记录 |
| `tutorial_step_complete` | A | 指定动作完成 | `step_id, step_index, duration_ms, mistake_count` | 同一步只完成一次，顺序异常报警 |
| `tutorial_complete` | A | 最后一步和进度均已保存 | `tutorial_version, total_duration_ms` | 保存成功后记录；不得因重装恢复重复发奖励 |

平台自动 `first_open` 只作为安装漏斗起点，应用不再自定义一个同义事件。

### 29.2 关卡与规则事件

| 事件 | 等级 | 触发时机 | 必需业务参数 | 验收口径 |
|---|---|---|---|---|
| `level_load_result` | A | 关卡读取、校验结束 | `level_entry_id, result, load_duration_ms, error_code` | `success/invalid_content/io_error/fallback_success`；失败不创建 Attempt |
| `level_start` | A | 棋盘完成展示且首次可操作 | `level_entry_id, attempt_no, start_reason, min_solution_steps, continue_used` | 每个 `attempt_id` 一次；`normal/retry/continue` |
| `level_resume` | B | 持久化中的 active Attempt 恢复可操作 | `level_entry_id, resume_reason, inactive_duration_ms` | 沿用原 `attempt_id`，不再发第二次 `level_start` |
| `vehicle_tap` | B | 规则层完成一次车身点击判定 | `vehicle_type, action_result, blocker_type, remaining_vehicle_count` | `safe_exit/collision/tutorial_demo/locked/ignored`；生产不上传精确坐标 |
| `vehicle_exit` | B | 合法离场动作提交 | `vehicle_type, trigger_types, remaining_required_count` | 动画回调不得重复上报 |
| `collision` | A | 计次碰撞提交 | `blocker_type, safety_before, safety_after, shield_used_in_chain` | 一次碰撞一次；动画回弹不重复上报 |
| `level_end` | A | 尝试达到唯一终态 | `result, end_reason, active_duration_ms, successful_action_count, collision_count, stars` | `result=complete/fail/quit/content_error`；`end_reason=goal_met/safety_zero/user_exit/restart/content_invalid`；每个 `attempt_id` 至多一个，正常闭环恰好一个 |
| `level_continue` | A | 广告奖励已入账且新尝试恢复成功 | `previous_attempt_id, new_attempt_id, continue_type, carried_collision_count` | 新尝试随后产生一个 `level_start` |
| `level_rule_deadlock` | A | 非终局且无合法动作 | `state_hash, remaining_vehicle_count, level_version` | 高优先级异常；不上传完整存档；给玩家免费修复/退出 |
| `optional_medal_result` | B | 可选时间徽章结算 | `medal_type, result, active_duration_ms, target_ms` | 超时不等于关卡失败 |

`active_duration_ms` 排除教学遮罩、暂停、后台、广告和系统中断。`successful_action_count` 只计玩家主动提交的离场或拖车，不计被拒绝点击和外部等待。

`level_end` 在非完成结果中固定 `stars=0`；完成结果的 `collision_count` 使用尝试链累计值，确保报表与最终星级一致。进程死亡本身不是终态：持久化为 active 的尝试恢复原 ID；若业务已终态但 `presentation_state` 未完成，只恢复结算/失败表现，不再发 `level_resume/level_start`。只有终态已经与 outbox 原子提交、但尚未送达时，才以原 `client_event_id` 重传。玩家手动重开先以 `result=quit, end_reason=restart` 结束旧尝试，再创建新尝试链；终态提交后不得再接收该 Attempt 的业务事件。

### 29.3 道具、经济与成长

| 事件 | 等级 | 触发时机 | 必需业务参数 | 验收口径 |
|---|---|---|---|---|
| `booster_offer_view` | B | 道具获取弹层真正可见 | `booster_type, offer_source, coin_price, ad_available` | 预创建 View 不算 |

## 31. 广告体验原则

1. 主线、免费重试、基础奖励和下一关永远不以广告加载成功为前提。
2. 强制广告只在明确自然断点出现；奖励广告必须由玩家主动选择并预先说明奖励。
3. L1–L10 的关卡结算均不展示插屏；首个可能的机会是 L11 结算，且累计有效游玩必须已达到 10 分钟。
4. 看完奖励广告 90 秒内不展示插屏。
5. 不在启动、关卡开始、失败、重试、游戏进行中、退出确认、购买或隐私流程后展示插屏。
6. 广告未准备好立即跳过；不显示等待广告的 Loading，不把奖励广告失败替换成插屏。
7. 每次只允许一个全屏广告流程；页面切换、应用后台或权益变化时重新验资格。
8. Native 使用固定标记区域和清晰“广告”标识；无填充时自然收起，不推动游戏关键按钮。

## 33. 广告资格、顺序和频控

广告资格拆为 `canPreload(format, placement)` 与 `canShow(format, placement, context)`，二者使用同一策略模块、同一版本配置，但条件不同。预加载不等于获得展示权，不能因为“已经加载”绕过展示复验。

### 33.1 共同门槛

任何广告 SDK 的加载或展示请求均需按顺序满足：

1. 配置整体通过版本、签名/来源、类型和范围校验；紧急关闭、总开关、格式开关与广告位开关均允许；
2. CMP 已解析且 `canRequestAds=true`；`ads_request_mode=blocked/unknown` 时不得发起任何广告请求；
3. `audience_mode` 已解析并允许当前网络/广告类型，`restricted/unknown` 默认关闭，除非发行审核提供显式受限路由；
4. 网络可用、Provider 配置有效且不在指数退避；同一 placement 没有未完成的重复加载；
5. 加载或展示不处于隐私/购买切换、应用退出或配置版本原子替换过程。

### 33.2 预加载门槛

- Interstitial：无去广告权益；玩家已进入或完成 L11；允许在预计的下一次自然结算前加载。预加载不要求当前已在结算页、不要求累计 600 秒、不检查关间隔/冷却/曝光上限，也不要求已有 `opportunity_id`。
- Rewarded：对应功能已经教学和解锁后才可预加载；预加载不要求玩家已经点击，但未绑定具体业务对象时不得创建奖励承诺。
- Native：首页/车库入口即将可见且已解锁、无去广告权益，并满足 60 秒最小加载间隔时可加载；不自动定时刷新。
- 每次决策创建 `preload_id`；加载成功只形成短期缓存，权益、同意、受众或紧急开关变化时立即销毁/失效。

### 33.3 展示门槛

Interstitial 在共同门槛外还必须全部满足：

1. 应用在前台、Activity 有效，来源 `mode=normal` 且非 Boss/救援/剧情/Hard 预览；奖励与进度动画已经完成，当前仍是同一个结算自然断点；
2. 无去广告权益，不处于购买、隐私、权限、另一个全屏广告或页面退出流程；
3. 教学已完成、来源显示关卡号 ≥11、累计有效游玩 ≥600 秒；
4. 若曾有插屏曝光，之后已完成至少 3 关；距上次插屏曝光 ≥120 秒，距奖励广告关闭 ≥90 秒；
5. 未达每会话 4 次、滚动 24 小时 8 次上限；首次安装会话另有 1 次上限；
6. `opportunity_id` 未消费、缓存仍有效且 Provider 不在退避；原子锁定机会后，再复验前台、页面、权益、同意与紧急开关。

Rewarded 展示不检查去广告权益、插屏的 L11/600 秒/关间隔/Boss 保护，但必须满足：功能已教学和解锁、按钮有本次真实用户点击、奖励内容与数量在点击前可见、业务快照有效且未消费、单点及全局上限未达、应用前台、全屏锁空闲、广告已准备。各广告位仍执行第 32 节自己的解锁限制。

Native 展示必须无去广告权益、处于稳定可见的首页/车库固定区域、入口已解锁、缓存与页面仍匹配，并满足合计每会话 8 次、滚动 24 小时 20 次曝光上限；不因滚动出入屏自动反复计曝光。

“累计有效游玩”定义为所有 Attempt 的 `active_duration_ms` 持久化累计，包含免费重试和广告续关；排除教学遮罩、暂停、后台、广告、首页、地图和结算。每段前台游戏用单调时钟计量，以不超过 30 秒的增量持久化；设备墙上时钟回拨不能减少累计值或绕过门槛。

首个会话即使达到其他条件，也最多展示 1 次插屏。所有会话/24 小时曝光频控仅在 SDK 官方曝光回调时原子消耗；Rewarded 的单业务奖励上限在 claim 首次 `earned` 时消耗，`prepared/retryable` 不消耗。加载失败、无填充和展示失败不消耗曝光频控，但当前插屏机会作废，不能跨页面补播。冷却使用单调时钟；滚动 24 小时使用持久化时间桶并与可信服务端时间校准，时钟损坏或明显回拨时按更严格结果关闭展示，不能重置上限。

`deny_reason` 枚举至少包括：

```text
none, placement_disabled, config_invalid, consent_pending, audience_restricted,
no_ads_entitled, app_not_foreground, activity_invalid, unsafe_screen,
fullscreen_busy, tutorial_protected, new_user_protected, level_gap,
cooldown, recent_rewarded, session_cap, daily_cap, boss_protected, mode_protected,
opportunity_consumed, offline, not_ready, provider_backoff, context_invalid,
user_action_missing, clock_untrusted
```

`limiting_cap_type` 封闭枚举为 `none/session/rolling_24h/placement/cooldown/level_gap/business`；没有命中上限时必须为 `none`，不能上传临时文案。

奖励广告全局上限为每会话 10 次、滚动 24 小时 20 次；其业务单点上限仍以第 32/35 节为准。

## 34. 奖励广告幂等流程

```text
展示明确奖励 → 玩家主动确认
→ prepared（持久化 claim 与奖励快照）
→ show_requested（展示调用成功发起）
→ earned（仅官方奖励回调/服务端验证可进入）
→ settling（账本事务进行中）
→ settled（奖励或补偿已且仅已入账一次）
```

加载/展示失败或关闭但未获奖励时进入未 earned 的 `retryable`；只有玩家再次明确点击，才可复用该 claim 发起新的 show attempt。业务上下文失效或玩家离开后进入 `cancelled/expired` 终态。任何本地超时、关闭回调、进程恢复或“播放时长足够”的推断都不得把 claim 变成 `earned`。

奖励快照至少包含 `placement_id`、`business_context_id`、`reward_type`、`reward_amount`、`reward_version`。业务去重键如下：

| 广告位 | `business_context_id` |
|---|---|
| `rv_hint` | `attempt_id + hint_offer_sequence` |
| `rv_continue_shield` | 失败的 `attempt_id` |
| `rv_tow` | `attempt_chain_id + target_vehicle_id`；另以链级 `tow_used` 保证整条链最多一次 |
| `rv_double_coins` | `completion_id` |
| `rv_daily_box` | `trusted_day_id`；优先取服务端日期，离线时沿用最后可信日期且不得跨日重复 |

- 关闭回调不发奖励；只有官方奖励回调或服务端验证进入账本。
- 除 `reward_claim_id` 主键外，奖励业务账本还必须唯一约束 `(placement_id, business_context_id, reward_version)`；重复回调、Activity 重建、断网重连和进程重启最多入账一次。未 `earned` 的展示失败可以复用同一 claim 重试或创建新的 show attempt，但不得创建第二条可结算业务键。
- 启动时只扫描 `earned/settling` 并继续结算，绝不扫描 `prepared/show_requested/retryable` 自动发奖；未确认记录只做 SDK/SSV 对账，在 Provider 规定的回调窗口内保留，仍无官方 earned 证据才转 `cancelled/expired`。经过认证的晚到 earned 证据必须仍按同一业务唯一键幂等补发。
- 回调确认但账本暂时写入失败时显示“奖励正在补发”，不能把广告标记为未看并要求重看。
- `earned` 永不因超时失效。提示/拖车若原 Attempt 已失效，则分别补发 1 个同类库存道具；续关若对应失败快照因版本迁移等不可恢复，则补发 1 个护盾并记录 `settle_result=compensated`；双倍金币和每日箱按不可变奖励快照直接入账。
- 正常情况下广告播放期间锁定业务上下文，用户不能同时免费重试、切换目标车或再次领取；晚到回调、先 close 后 reward、重复 reward 和重启后回调都必须纳入自动化测试。
- 双倍金币只追加基础金币等额奖励，基础金币在广告前已经到账。

## 36. 去广告权益与当前模板差距

建议 P1 提供永久商品 `remove_ads_lifetime`，仅在该 P1 功能启用时适用。商品页明确说明：

> 移除所有非自愿或展示型广告，包括插屏、原生广告，以及未来如启用的开屏/Banner；自选奖励广告仍可使用。

权益生效后立即拒绝所有被移除格式、取消进行中的 Native 请求、销毁已缓存插屏/Native，并收起首页/车库广告容器；奖励广告保留为自愿入口。权益需支持启动校验、主动恢复、已验证权益离线缓存、退款/撤销回收和重复回调幂等。

购买状态以 `purchase_record_id` 管理：Play 返回 `PENDING` 时不授予权益；`PURCHASED` 必须验证通过后再授予并按 Billing 要求确认；启动查询、主动恢复、退款和撤销均更新同一记录。原始 purchase token 仅作为安全存储/服务端的唯一核验键，不进入 Analytics、日志或崩溃附件；`billing_session_id` 只描述一次 UI 流程，不作为交易去重键。

当前模板已经具备 Launcher、广告初始化和基础广告包装，但正式实现前必须补齐并验证：

- 统一奖励广告业务接口及官方奖励回调；
- 广告资格、全局全屏锁、频控持久化和 Provider 退避；
- 奖励账本与 `reward_claim_id` 恢复；
- Play Billing 和去广告权益（当前不应假设已存在）；
- 所有广告事件的统一路由，避免聚合层和应用层重复上报。

这些能力属于独立基础模块，不应以页面扩展函数或散落回调补丁实现。

## 37. 隐私与广告合规需求

- 每次启动先更新同意信息；在 UMP/CMP 给出 `canRequestAds=true` 之前不得初始化会发网请求的广告链路、预加载或请求任何广告，不只是禁止个性化广告。应使用符合适用规则的认证 CMP/同意框架。
- 设置页长期提供“隐私选项”，用户修改后同步所有广告 SDK，而不是只同步一个网络。
- 不在 Analytics/Crashlytics 上传姓名、邮箱、手机号、精确位置、原始广告标识符、原始 CMP 字符串、完整存档、购买令牌或完整订单号。
- 产品默认定位一般休闲受众、13+、家庭友好但不声明为儿童定向。若未来改为儿童或混合受众，必须重新审核 SDK、个性化广告、商店受众声明和 Families 要求。
- Native 清晰标注“广告”；不得模仿车辆、奖励、系统通知或放置假关闭按钮。
- 商店 Data Safety、隐私政策、CMP 选项和 SDK 实际收集行为必须一致。
- 用户撤回 Analytics 同意时停止后续采集并删除未发送分析 outbox；删除账号/本地数据时清除可删除进度、广告频控、待加载缓存和分析 ID，但依法/履约必须保留的购买记录单独说明保留期限。备份恢复后必须重新验证同意、受众和购买权益，不能沿用旧广告许可。
- 目标 API、广告 SDK、同意 SDK、Billing 和商店政策在每次提审前重新核验，不把本文日期时的状态视为永久规则。

### 41.1 必须采用的启动门控顺序

1. 对每个 release variant 生成合并 Manifest/启动组件清单，审查外部 Launcher `Application.super.onCreate()`、所有 ContentProvider、AndroidX Startup Initializer、Receiver/Service、备份属性和 SDK metadata；在进程创建前通过官方开关、Manifest 移除/替换或供应方延迟接口阻止可选 SDK 自动初始化。无法控制的父 Application 发网或未经验证的 `restoreAnyVersion` 属于发布阻塞项。
2. 进程最早阶段使用 Manifest/SDK 默认配置关闭可选 Analytics、Crashlytics、归因和广告自动采集；只读取本地版本化隐私状态，不初始化可能发网的业务 reporter/广告 Provider。
3. 每次启动调用 CMP/UMP 的 consent info update，并解析 `analytics_collection_state`、`ads_request_mode/canRequestAds`、隐私选项入口要求和 `audience_mode`。受众 unknown 按受限处理。
4. Analytics、Crashlytics、ThinkingData、Adjust 分别通过用途门控后再启用；广告只在 `canRequestAds=true` 且受众路由允许后初始化、加载、竞价或展示。某个用途获准不得推导其他用途也获准。
5. 同意变化时广播给所有已启用 SDK：撤回则停止采集、清除未发送分析 outbox、销毁广告缓存并重算资格；恢复授权也不得补传拒绝期间行为。
6. 使用抓包/代理在冷启动、首次安装、拒绝、撤回、受众 unknown、离线恢复六条路径验收：门控前广告请求为 0，可选分析/归因请求符合选择，且不会先初始化后再补设置。

`AnalyticsRouter` 只允许非阻塞入队；现有 reporter 中的 `runBlocking`/等待 SDK 就绪逻辑不得进入主线程点击、规则提交、奖励或购买事务路径。SDK 不可用时记录异步诊断并稍后投递，不能拖慢 `<100 ms` 输入反馈。

### 41.2 备份与数据迁移矩阵

| 数据类别 | 系统云备份/设备迁移 | 恢复动作 |
|---|---|---|
| 版本化关卡进度、已拥有外观、已结算奖励账本 | 可 include；需加密/校验并控制 schema 版本 | 迁移后做一致性校验，冲突时保守保留已验证拥有项 |
| Play 权益缓存 | 不作为最终凭据 | 重新查询 Billing/后端验证，再更新同一 `purchase_record_id` |
| CMP 原始字符串、受众状态、广告许可 | exclude | 在新安装/设备重新更新同意信息和受众路由 |
| 所有未 earned 的 claim/show-attempt（`prepared/show_requested/retryable/cancelled/expired`）、SDK 广告缓存、广告频控、install/session/AAID 派生 ID | exclude | 不恢复、不补发；重新创建本机会状态 |

| Analytics outbox、Crash 附件、原始 purchase token | exclude | outbox 不跨设备补传；token 只从 Billing/安全后端重新取得或核验 |

## 44. 版本变更规则

- 本文进入评审后，锁定规则变更必须提交变更单，列出对关卡包、标准解、存档、埋点、广告、测试和旧版本兼容的影响。
- 纯数值调整更新 `balance_version` 或 `ads_config_version`；关卡布局调整更新 `level_version`；基础语义调整更新 `rule_version`。
- 已开始的关卡固定使用进入时的内容和规则版本；远程更新从下一次进入生效。
- 每次正式关卡包发布保留上一个稳定包、验证报告、变更摘要和一键回退能力。
- 文档从 Draft 进入 Approved 前，产品、客户端、关卡、测试、数据和商业化负责人必须共同签字。

**文档结论：** 首发应先把“点击—判定—清场”的确定性体验、可批量验证的关卡生产、可靠存档和克制广告做扎实。前 30 关已经给出机制教学和节奏基线；后续 90–120 关应沿用同一规则与审核工具扩展，而不是通过增加随机性、广告依赖或隐藏限制制造难度。
